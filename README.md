# BroomBuster

![GrimSweeper](frontend/grim_sweeper_rect.webp)

Know before the grim sweeper comes. An interactive map that shows your parked car and tells you whether street sweeping applies to that block — today, tomorrow, or not at all.

## Features

- **Multi-car tracking** — save multiple cars, each with its own name, color, and location.
- **GPS** — one tap to move a car to your phone's current GPS position.
- **Manual placement** — tap anywhere on the map to place a car.
- **Urgency color coding** — streets and car cards color-coded by sweeping urgency:
  - Red — sweeping today
  - Orange — sweeping tomorrow
  - Blue — no sweeping soon
- **Live status banner** — top bar shows which cars need to move.
- **Multi-city / multi-region** — Bay Area (Oakland, SF, Berkeley, Alameda) and Chicago.
- **Python CLI** — the original command-line tool still works independently.

## How to run

### Web app (local)

```bash
uv sync --locked --extra api   # creates .venv
./run.sh
```

`./run.sh` starts the server with `DEV_MODE=true` (no login, no `JWT_SECRET`)
and opens `http://localhost:8000`. Override with `PORT=8080 ./run.sh` or
`PYTHON=/path/to/python ./run.sh`. The map renders from the PMTiles vector tiles
committed in `frontend/tiles/`.

### Developer install (tests, ruff, build scripts)

```bash
uv sync --locked --all-extras
uv run pytest        # JS↔Python parity tests also run when `node` is on PATH
```

Frontend map libraries (MapLibre GL, PMTiles) are vendored in `frontend/vendor/`;
refresh them with `scripts/update_vendor.sh` (also bumps `CACHE` in `frontend/sw.js`).

### Python CLI

```bash
python -m broombuster.cli.main --lat 37.8213 --lon -122.2807
python -m broombuster.cli.main --region chicago --notify --loop   # email (EMAIL_* in .env)
```

Prints the street and both sides' schedules for a parked spot, using the same
resolver and sweeping plugin as the web app.

## Deployment

Production runs on an always-on Raspberry Pi 5 under `systemd`, published on
the internet with Tailscale Funnel and rolled out automatically from `main`
once CI passes. Setup and operations: [`deploy/README.md`](deploy/README.md).

| Aspect | Behaviour |
|--------|-----------|
| Guests (no login) | Anyone can browse the map and add cars/homes. Guest data stays in that browser tab. |
| Shared account | One seeded login you can hand out; everyone signed into it shares one server-saved set of cars/homes. |
| Self-registration | **Disabled** unless `ALLOW_REGISTRATION=true`. |
| Secrets | `JWT_SECRET` lives in `.env` (gitignored), generated by `deploy/install-service.sh`. |

**Seed / reset the shared account** (on the server, against the same DB):

```bash
SEED_EMAIL=share@broombuster SEED_PASSWORD='a-strong-passphrase' \
  .venv/bin/python scripts/seed_account.py     # omit SEED_PASSWORD to auto-generate one
```

Behind your own TLS proxy instead, run the API directly:

```bash
JWT_SECRET=$(python -c "import secrets; print(secrets.token_hex(32))") \
  uvicorn broombuster.api.app:app --host 127.0.0.1 --port 8000
```

## Continuous integration

One GitHub Actions workflow, [`.github/workflows/ci.yml`](.github/workflows/ci.yml),
runs `ruff check` and the full `pytest` suite on every PR and push to `main`.
Deployment is pull-based: the Pi's auto-update timer rolls out a new `main`
commit only after `ci.yml` has passed on it.

## Refreshing city data

City `.fgb` files are what the server reads; each manifest's `source:` block
says where the raw input comes from. To regenerate:

```bash
python scripts/rebuild_city_data.py <city_key>     # one city (or omit for all)
python scripts/build_pmtiles.py                    # then the map tiles (needs tippecanoe)
```

Commit the rebuilt `.fgb` and tiles; deployments ship data through git. `/health`
reports the data age of cities with `stale_after_days` (from the file's last
commit) and flags it `stale`. See [`data/README.md`](data/README.md).
